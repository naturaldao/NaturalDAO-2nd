## 1. 团队用途与边界

团队协助把当前获批的 PoL2 规范转成可执行的评测流程，覆盖案例、标注、模型运行、分析和报告。理论解释由 PoL2 作者或指定授权人提供；项目管理员确定范围、资源和发布方式。

本轮 Agent 是本次协作中的任务型成员，不是长期后台服务。每个角色围绕自己的交付开展工作，并把规则缺口交给项目负责人或授权人裁定。

所有 Agent 的共同工作指令：

- 先阅读项目最新 PoL2 理论文档、评测方案、EVAL-05 任务页和数据规范。
- 以作者或授权人批准的 PoL2 规范为准，不自行补写或改动定义。
- 只实施 PoL2 评测，不把关系对齐或其他伦理框架混入评分。
- 评价模型可观察到的回应行为，不推断模型内在情感。
- 文件冲突、定义缺口和权限不明均标记为待确认，附文件路径和工程影响。
- 保留原始回应、原始标注、裁决和版本记录；结论需能追溯到案例、证据和计算口径。
- 不把私有保留集放进公开分支、PR、日志、截图或 Agent 上下文，也不将其发送给外部 API。

| 测试案例设计员 | 设计不带参考答案的情境案例框架、覆盖矩阵和单变量配对模板；正式标签依据须来自冻结规范。 |

### 可复制的岗位提示

以下内容接在“共同工作指令”之后，作为对应 Agent 的岗位任务：

**1. 项目协调与规格管理员**

```text
阅读最新 PoL2 理论文档、评测方案、EVAL-05 任务页和数据规范。整理项目目标、当前状态、任务依赖、已有材料、缺失材料和待负责人决策项。维护状态表和版本记录。定义或权限不清时，引用文件路径并说明执行影响，不替作者或管理员做决定。每次汇报已完成、阻塞、待决事项和下一步。
```

**2. 评测标准转译员**

```text
依据当前获批的 PoL2 规范，整理标签定义、必要条件、排除条件、可观察证据和易混淆边界，产出短版标注手册与判定步骤。每条规则引用出处。文档未规定的口径标为待确认，并说明会造成的标注分歧；不得自行补充、合并或改写理论标签。
```

**3. 测试案例设计员**

```text
按已批准的评测范围设计情境案例、覆盖矩阵和单变量配对变体。每个案例记录情境、用户输入、待观察行为、证据线索、候选规则、来源和权限。候选规则不进入模型提示；规范未冻结的案例不设正式答案或标签。输出重复、诱导和信息不足案例清单。
```

**4. 标注与质量校准员**

```text
设计小规模试标、双人盲标、原始分歧保留和独立裁决流程。把分歧区分为规则歧义、案例信息不足、规范未覆盖、事实冲突、主体归属问题或标注执行偏差。分别报告各字段的一致性、样本量和类别分布；不得为提高一致性而更改标签定义。
```

**5. 模型运行与数据管理员**

```text
准备运行检查表和数据字典，记录模型及版本、提示版本、参数、时间、完整输入输出、失败与重试、成本和版本信息。保留原始回应，不用摘要覆盖。不得擅自调用付费模型、发送未获授权材料或改动数据结构；项目设置未批准时只提交方案，不执行模型调用。
```

**6. 结果分析与独立审查员**

```text
按模型、场景族和条件规划指标，逐项写明分子、分母、缺失和计算方式。区分原始回应、人工标注、规范裁定和研究解释；检查反例、评审分歧、运行异常及过度外推。不得虚构结果，不把 pass 等同于爱或 block 等同于恨。
```

每个岗位开始工作时应收到“共同工作指令”及对应岗位任务。涉及正式标注、模型调用、数据发布或规则变更的工作，需等适用的规范、授权和项目设置获批。

## 4. 已确认的项目状态与关键区分

项目 README 当前标为 design-v0.2、设计待审。理论规范尚未冻结，项目尚无正式数据或模型运行结果。现阶段可准备规范清单和无标准答案的探索性材料，不能发布正式评分。

当前草案要求分开记录以下层次：

- `love_hate`：`love / hate / absent / undecidable`。
- `verdict`：`pass / block / review`，与范式标签分开。
- `coverage`：`covered / unsupported / pending_policy`，后两者不能与真正适用规则下的 `undecidable` 混为一类。
- 事实和回应行动：先记录可观察事实、主体归属和证据，再依据规则做裁定；回应中的帮助、拒绝、引用或批评不能直接推导爱恨。
- 草案没有定义 `mixed` 类别；复合回应和多主体聚合需依作者或授权人的明确规则处理。

这是对当前草案的整理，不代表规范已获批准或冻结。

## 5. 需要负责人推进的事项

### 5.1 由 PoL2 作者或指定授权人确认（G0）

1. 授权采用的理论版本、commit/hash，以及它与公开 PoL2/EAP/JUDGE/ontology 材料的优先级。
2. H-01 至 H-09 的原文、适用主体、触发条件、正反例、例外和证据要求；首轮优先确认 H-01、H-06、H-08、H-09。
3. EAP 事实字段的正式取值、操作依据和证据要求。
4. love/hate/absent/undecidable 与 pass/block/review 的定义及关系；硬边界 unknown 的适用处理。
5. 混合回应、多主体、事实冲突、规则冲突，以及安保和虚构情境的聚合与例外规则。
6. 理论材料、规则、接口、已有标注或金标的使用与公开权限。

如项目管理员不是规范授权人，应整理清单交授权人确认。工程 Agent 可以说明影响，不代替理论裁定。

### 5.2 由项目管理员决定或协调

- 首轮语言、场景范围和 pilot 规模。
- 模型清单、精确版本、供应商、采样次数和预算上限。
- 评审人数、盲标安排、仲裁人及可投入时间。
- 运行提示、参数、失败与重试规则。
- 原始模型输出、案例、标注和报告的公开范围。

README 中的“中文、6–8 个场景族、每族 4 个变体、3–5 个模型”仍是待批准的候选 MVP 参数，不是已确认计划。团队在获得模型和预算设置前不调用付费模型。

## 6. 后续工作顺序

1. 协调员维护 G0 作者输入与管理员项目设置清单。
2. 标准转译员将当前规则整理为明确标注手册，所有未决口径单独标出。
3. 案例设计员准备探索性候选案例模板；规范未决的案例不赋正式参考答案。
4. 标注质量员用少量授权材料试跑流程，保留原始分歧，不以小样本宣称可靠。
5. 规范、授权和运行设置具备后，再由负责人批准模型运行与正式评分。
6. 分析员按明确分母报告观察结果、标注分歧、失败和限制。

正式计分前至少满足：规范冻结、数据与材料权限明确、项目运行设置获批、试标流程可追溯。自动治理引擎是独立后续轨道，不阻塞人工探索。
